# 开发帮助

本页面向 Freqtrade 的开发者、希望为 Freqtrade 代码库或文档做出贡献的人，以及希望了解他们正在运行的应用程序源代码的人。

欢迎所有的贡献、错误报告、错误修复、文档改进、功能增强和创意。我们在 [GitHub](https://github.com) 上 [跟踪 Issue](https://github.com/freqtrade/freqtrade/issues)，并在 [Discord](https://discord.gg/p7nuUNVfP7) 上有一个开发频道，您可以在那里提问。

## 文档

文档可在 [https://freqtrade.io](https://www.freqtrade.io/) 获取，每个新功能 PR 都需要提供相应的文档。

文档的特殊字段（如 Note 框等）可以在 [此处](https://squidfunk.github.io/mkdocs-material/reference/admonitions/) 找到。

要在本地测试文档，请使用以下命令：

``` bash
pip install -r docs/requirements-docs.txt
mkdocs serve
```

这将启动一个本地服务器（通常在 8000 端口），以便您可以查看一切是否符合您的预期。

## 开发者设置

要配置开发环境，您可以使用提供的 [DevContainer](#devcontainer-设置)，或者使用 `setup.sh` 脚本并在询问 "Do you want to install dependencies for dev [y/N]? " 时回答 "y"。
或者（例如，如果您的系统不支持 `setup.sh` 脚本），请遵循手动安装过程并运行 `pip3 install -r requirements-dev.txt`，然后运行 `pip3 install -e .[all]`。

这将安装开发所需的所有工具，包括 `pytest`、`ruff`、`mypy` 和 `coveralls`。

运行以下命令安装 git hook 脚本：

``` bash
pre-commit install
```

这些 pre-commit 脚本会在每次提交前自动检查您的更改。
如果发现任何格式问题，提交将失败并提示修复。
这减少了不必要的 CI 失败，降低了维护负担，并提高了代码质量。

必要时，您可以使用 `pre-commit run -a` 手动运行检查。

在开启拉取请求（Pull Request）之前，请先熟悉我们的 [贡献指南](https://github.com/freqtrade/freqtrade/blob/develop/CONTRIBUTING.md)。

### Devcontainer 设置

最快且最容易开始的方法是使用 [VSCode](https://code.visualstudio.com/) 及其 Remote Container 扩展。
这使开发者能够启动带有所有必需依赖项的机器人，而*无需*在本地机器上安装任何特定的 Freqtrade 依赖项。

#### Devcontainer 依赖

* [VSCode](https://code.visualstudio.com/)
* [docker](https://docs.docker.com/install/)
* [Remote container 扩展文档](https://code.visualstudio.com/docs/remote)

有关 [Remote container 扩展](https://code.visualstudio.com/docs/remote) 的更多信息，最好咨询其文档。

### 测试

新代码应由基础单元测试（unittest）覆盖。根据功能的复杂程度，审阅者（Reviewer）可能会要求更深入的单元测试。
如有必要，Freqtrade 团队可以在编写好的测试方面提供协助和指导（但请不要指望有人为您编写测试）。

#### 如何运行测试

在根目录下使用 `pytest` 运行所有可用的测试用例，并确认您的本地环境配置正确。

!!! Note "功能分支"
    测试预计在 `develop` 和 `stable` 分支上通过。其他分支可能是正在进行的工作，测试可能尚无法运行。

#### 在测试中检查日志内容

Freqtrade 使用 2 种主要方法来检查测试中的日志内容：`log_has()` 和 `log_has_re()`（用于使用正则表达式检查动态日志消息）。
这些方法可从 `conftest.py` 获得，并可以导入到任何测试模块中。

示例检查如下所示：

``` python
from tests.conftest import log_has, log_has_re

def test_method_to_test(caplog):
    method_to_test()

    assert log_has("This event happened", caplog)
    # 使用正则表达式检查带有尾随数字的内容 ...
    assert log_has_re(r"This dynamic event happened and produced \d+", caplog)

```

## 错误处理

Freqtrade 异常都继承自 `FreqtradeException`。
然而，不应直接使用这个通用的错误类。相反，存在多个专门的子异常。

以下是异常继承层级的概述：

```
+ FreqtradeException
|
+---+ OperationalException
|   |
|   +---+ ConfigurationError
|
+---+ DependencyException
|   |
|   +---+ PricingError
|   |
|   +---+ ExchangeError
|       |
|       +---+ TemporaryError
|       |
|       +---+ DDosProtection
|       |
|       +---+ InvalidOrderException
|           |
|           +---+ RetryableOrderError
|           |
|           +---+ InsufficientFundsError
|
+---+ StrategyError
```

### 交易对列表（Pairlists）

您有一个关于新的交易对选择算法的好主意并想尝试一下？太棒了。
希望您也想将其贡献回上游。

无论您的动机是什么，这都应该能让您开始尝试开发一个新的 Pairlist 处理器（Handler）。

首先，查看 [VolumePairList](https://github.com/freqtrade/freqtrade/blob/develop/freqtrade/plugins/pairlist/VolumePairList.py) 处理器，最好以您新的 Pairlist 处理器的名称复制此文件。

这是一个简单的处理器，但它是开始开发的一个很好的例子。

接下来，修改处理器的类名（理想情况下与模块文件名一致）。

基类提供了一个交易所实例 (`self._exchange`)、交易对列表管理器 (`self._pairlistmanager`)，以及主配置 (`self._config`)、交易对列表专用配置 (`self._pairlistconfig`) 和在交易对列表序列中的绝对位置。

```python
        self._exchange = exchange
        self._pairlistmanager = pairlistmanager
        self._config = config
        self._pairlistconfig = pairlistconfig
        self._pairlist_pos = pairlist_pos
```

!!! Tip "小提示"
    别忘了在 `constants.py` 的变量 `AVAILABLE_PAIRLISTS` 下注册您的交易对列表，否则它将无法被选择。

现在，让我们逐步了解需要操作的方法：

#### 交易对列表配置

交易对列表处理器链的配置是在机器人配置文件的 `"pairlists"` 元素中完成的，它是链中每个交易对列表处理器的配置参数数组。

按照惯例，`"number_assets"` 用于指定要在交易对列表中保留的最大对数。请遵循此约定以确保一致的用户体验。

可以根据需要配置其他参数。例如，`VolumePairList` 使用 `"sort_key"` 来指定排序值 - 但请随意指定您的算法成功和动态运行所需的任何参数。

#### short_desc

返回用于 Telegram 消息的描述。

这应包含交易对列表处理器的名称，以及包含资产数量的简短描述。请遵循格式 `"PairlistName - top/bottom X pairs"`。

#### gen_pairlist

如果该交易对列表处理器可以用作链中的主导处理器，定义初始交易对列表并随后由链中所有处理器处理，请重写此方法。示例包括 `StaticPairList` 和 `VolumePairList`。

该方法在机器人的每次迭代中被调用（仅当该处理器位于第一个位置时）- 因此请考虑为计算量大或网络消耗大的计算实现缓存。

它必须返回生成的交易对列表（随后可能会传递到交易对列表处理器链中）。

验证是可选的，父类预留了 `verify_blacklist(pairlist)` 和 `_whitelist_for_active_markets(pairlist)` 用于执行默认过滤。如果您将结果限制为一定数量的对，请使用这些方法 - 这样最终结果不会短于预期。

#### filter_pairlist

该方法由交易对列表管理器为链中的每个交易对列表处理器调用。

该方法在机器人的每次迭代中被调用 - 因此请考虑为计算量大或网络消耗大的计算实现缓存。

它会接收到一个交易对列表（可以是之前处理器的结果）以及 `tickers`（`get_tickers()` 的预取版本）。

基类中的默认实现只是对列表中的每个交易对调用 `_validate_pair()` 方法，但您可以重写它。因此，您应该在您的处理器中实现 `_validate_pair()`，或者重写 `filter_pairlist()` 来执行其他操作。

如果重写，它必须返回生成的交易对列表（随后可能会传递到链中的下一个处理器）。

验证是可选的，父类预留了 `verify_blacklist(pairlist)` 和 `_whitelist_for_active_markets(pairlist)` 用于执行默认过滤。如果您将结果限制为一定数量的对，请使用这些方法 - 这样最终结果不会短于预期。

在 `VolumePairList` 中，这实现了不同的排序方法，并进行了早期验证，以便仅返回预期数量的对。

##### 示例

``` python
    def filter_pairlist(self, pairlist: list[str], tickers: dict) -> List[str]:
        # 生成动态白名单
        pairs = self._calculate_pairlist(pairlist, tickers)
        return pairs
```

### 保护 (Protections)

最好阅读 [保护文档](plugins.md#protections) 以理解保护功能。
本指南面向希望开发新保护功能的开发者。

保护功能不应直接使用 `datetime`，而应使用提供的 `date_now` 变量进行日期计算。这保留了对保护功能进行回测的能力。

!!! Tip "编写新的保护功能"
    最好复制现有的保护功能之一作为参考示例。

#### 实现新的保护功能

所有保护功能的实现必须以 `IProtection` 作为父类。
因此，它们必须实现以下方法：

* `short_desc()`
* `global_stop()`
* `stop_per_pair()`。

`global_stop()` 和 `stop_per_pair()` 必须返回一个 `ProtectionReturn` 对象，该对象包含：

* lock pair - 布尔值
* lock until - datetime - 锁定到什么时候（将向上舍入到下一个新 K 线）
* reason - 字符串，用于日志记录和数据库存储
* lock_side - long, short 或 '*'。

`until` 部分应使用提供的 `calculate_lock_end()` 方法计算。

所有保护功能应使用 `"stop_duration"` / `"stop_duration_candles"` 来定义一个对（或所有对）应锁定多长时间。
其内容将作为 `self._stop_duration` 提供给每个保护功能。

如果您的保护功能需要回看期（look-back period），请使用 `"lookback_period"` / `"lockback_period_candles"` 以保持所有保护功能一致。

#### 全局停顿 vs. 局部停顿

保护功能可以通过 2 种不同的方式在有限时间内停止交易：

* 按交易对（局部）
* 针对所有交易对（全局）

##### 局部保护（按交易对）

实现局部停顿方法的保护功能必须设置 `has_local_stop=True`。
每当交易关闭（离场订单完成）时，将调用 `stop_per_pair()` 方法。

##### 全局保护

这些保护功能应在所有交易对上进行评估，并因此锁定所有交易对的交易（称为全局交易对锁定）。
全局保护功能必须设置 `has_global_stop=True` 才能进行全局停顿评估。
每当交易关闭（离场订单完成）时，将调用 `global_stop()` 方法。

##### 计算锁定结束时间

保护功能应根据其考虑的最后一次交易来计算锁定结束时间。
这可以避免如果回看期长于实际锁定周期而导致重新锁定。

`IProtection` 父类在 `calculate_lock_end()` 中为此提供了一个辅助方法。

### 不完整的 K 线

在获取 K 线 (OHLCV) 数据时，我们最终可能会得到不完整的 K 线（取决于交易所）。
为了演示这一点，我们将使用日 K 线 (`"1d"`) 来简化。
我们向 API (`ct.fetch_ohlcv()`) 查询该时间范围并查看最后一项的日期。如果此项发生了变化或者显示的是一根 "不完整" K 线的日期，那么我们应该将其丢弃，因为拥有不完整 K 线是有问题的，因为指标（Indicator）假定只向它们传递完整 K 线，否则会产生很多虚假的买入信号。因此，缺省情况下，我们假设最后一根 K 线是不完整的并将其移除。

要检查新交易所的行为，您可以使用以下代码片段：

``` python
import ccxt
from datetime import datetime, timezone
from freqtrade.data.converter import ohlcv_to_dataframe
ct = ccxt.binance()  # 使用您正在测试的交易所
timeframe = "1d"
pair = "BTC/USDT"  # 确保使用的是在该交易所存在的交易对！
raw = ct.fetch_ohlcv(pair, timeframe=timeframe)

# 转换为 dataframe
df1 = ohlcv_to_dataframe(raw, timeframe, pair=pair, drop_incomplete=False)

print(df1.tail(1))
print(datetime.now(timezone.utc))
```

``` output
                         date      open      high       low     close  volume  
499 2019-06-08 00:00:00+00:00  0.000007  0.000007  0.000007  0.000007   26264344.0  
2019-06-09 12:30:27.873327
```

输出将显示来自交易所的最后一项以及当前的 UTC 日期。
如果日期显示为同一天，那么可以假设最后一根 K 线是不完整的，应当丢弃（保持交易所类中的设置 `"ohlcv_partial_candle"` 不变/为 True）。否则，将 `"ohlcv_partial_candle"` 设置为 `False` 以便不丢弃 K 线（如上例所示）。
另一种方法是连续多次运行此命令，观察成交量是否在变化（而日期保持不变）。

## 持续集成 (CI)

本节记录了针对 CI 管线做出的一些决定。

* CI 在所有操作系统变体上运行，包括 Linux (Ubuntu)、macOS 和 Windows。
* 为分支 `stable` 和 `develop` 构建 Docker 镜像，并构建为多架构（multiarch）构建，通过同一个标签支持多个平台。
* 包含绘图（Plot）依赖项的 Docker 镜像也以 `stable_plot` 和 `develop_plot` 的形式提供。
* Docker 镜像包含一个文件 `/freqtrade/freqtrade_commit`，其中包含了该镜像所基于的 commit。
* 每周通过计划任务运行一次完整的 Docker 镜像重构。
* 部署在 Ubuntu 上运行。
* 一个 PR 必须通过所有测试才能合并到 `stable` 或 `develop`。

## 创建发行版 (Release)

文档的这一部分面向维护者，展示了如何创建一个发行版。

### 创建发行分支

!!! Note "注意"
    确保 `stable` 分支是最新的！

首先，选取一个大约一周前的 commit（以不包含最新添加到发行版中的内容）。

``` bash
# 创建新分支
git checkout -b new_release <commitid>
```

确定在该 commit 与当前状态之间是否进行了关键的错误修复，最终择优挑选（cherry-pick）这些修复。

* 将发行分支 (stable) 合并到该分支中。
* 编辑 `freqtrade/__init__.py` 并添加与当前日期匹配的版本（例如 `2025.7` 代表 2025 年 7 月）。如果该月需要进行第二次发行，小版本号可以是 `2025.7.1`。版本号必须遵循 PEP0440 允许的版本，以避免在推送到 PyPI 时失败。
* 提交这部分内容。
* 将该分支推送到远程并针对 **stable 分支** 创建一个 PR。
* 按照 `2025.8-dev` 模式将 develop 版本更新到下一个版本。

### 从 Git Commit 创建更改日志 (Changelog)

``` bash
# 需要在合并/拉取该分支之前完成。
git log --oneline --no-decorate --no-merges stable..new_release
```

为了保持发行日志简短，最好将完整的 Git 更改日志包装在可折叠的详情（details）部分中。

```markdown
<details>
<summary>展开完整更改日志</summary>

... 完整的 Git 更改日志

</details>
```

### FreqUI 发行版

如果 FreqUI 进行了实质性的更新，请确保在合并发行分支之前创建一个发行版。
确保 FreqUI CI 在发行版上完成并通过，然后再合并发行分支。

### 创建 GitHub Release / Tag

一旦针对 stable 的 PR 被合并（最好在合并后立即）：

* 使用 GitHub 界面中的 "Draft a new release" 按钮（releases 子节）。
* 使用作为标签（Tag）指定的版本号。
* 使用 "stable" 作为引用（此步骤发生在上述 PR 合并之后）。
